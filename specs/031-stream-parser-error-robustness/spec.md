# Feature Specification: 스트림 파서 견고화 — `error` 이벤트를 종결로 오인하지 않기

**Feature Branch**: `031-stream-parser-error-robustness`

**Created**: 2026-06-27

**Status**: Draft

**Input**: 전수조사(스트림)에서 발견한 잠재 결함: NDJSON 스트림 파서가 데이터성 `error` 이벤트를 **스트림 종결 신호로 오인**해, 그 이벤트가 든 청크의 **나머지 라인을 버린다**. 현재는 백엔드가 `error`를 종결 지점에서만 보내 무해(잠재)하나, 비종결 `error`가 오면 라이브 이벤트가 유실될 수 있다. 견고성 1줄 수정.

## 배경 / 현재 동작

분석 스트림(NDJSON)은 한 줄=한 이벤트로 파싱되어 콜백에 전달된다. 파서는 한 이벤트의 `type`이 `complete` 또는 `error`이면 **그 시점에서 버퍼를 비우고 그 청크의 잔여 라인·부분 라인을 버린다**(스트림 종결로 간주).

**확인된 사실(코드)**: 분석 스트림의 실제 종결은 **연결 종료(HTTP done) 또는 `stream_end`** 이며, `error`는 **데이터성 이벤트**(콘솔에 표시될 진행/오류 메시지)다. 백엔드는 현재 스트림으로 가는 `error`를 **파이프라인 종결 지점에서만** 보내(직후 중단), 그래서 잔여 폐기가 무해하다. 그러나 만약 비종결 `error`(분석 계속 중 한 건 실패 보고 등)가 스트림에 실리면, **같은 청크의 뒤따르는 노드/관계/진행 이벤트가 조용히 유실**된다. 즉 파서가 `error`를 종결로 보는 것은 **설계상 부정확**하다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 오류가 떠도 그래프가 빠지지 않는다 (Priority: P1)

분석 도중 오류 메시지 한 줄이 스트림에 실려도, 사용자의 라이브 그래프·진행 표시에서 **그 직후의 노드/관계가 사라지지 않는다**. 오류는 콘솔에 표시되고, 스트림은 정상 종료(연결 종료) 시까지 계속 소비된다.

**Why this priority**: 데이터 유실 방지. 현재는 잠재(백엔드가 종결 error만 보냄)지만, 파서 정확성은 회귀 안전망의 기본.

**Independent Test**: NDJSON 라인 시퀀스에 중간 `error` 이벤트 + 그 뒤 노드/관계 이벤트를 같은 청크로 넣어 파싱 → 뒤 이벤트가 콜백에 **모두 전달**되는지 확인.

**Acceptance Scenarios**:

1. **Given** 한 청크에 `[node, error, node, relationship]` 라인이 들어옴, **When** 파싱, **Then** 4개 이벤트가 **모두** 콜백에 전달된다(현재는 error 이후 2개 유실).
2. **Given** 스트림이 연결 종료(HTTP done)로 끝남, **When** 파싱 종료, **Then** 종료가 정상 처리된다(`error` 의존 없이).
3. **Given** 다른 스트림 소비처(파싱 등)가 `complete`를 종결로 씀, **When** `complete` 도착, **Then** 기존 동작 유지(회귀 없음).

### Edge Cases
- 부분 라인(청크 경계에 걸친 JSON) → 다음 청크와 합쳐 파싱(현행 유지, `error`로 인한 조기 폐기 제거).
- 손상된 JSON 라인 → 건너뛰고 계속(현행 유지).
- 진짜 종결(`stream_end`/HTTP done) → 정상 종료.

## Requirements *(mandatory)*

- **FR-001**: 스트림 파서는 데이터성 `error` 이벤트를 **스트림 종결로 취급하지 않아야** 한다(그 청크의 잔여·부분 라인 폐기 금지). `error`는 다른 이벤트처럼 콜백에 전달된다.
- **FR-002**: 스트림 종결은 **연결 종료(HTTP done)** 로 처리한다(현행 reader 루프). `complete`를 종결로 쓰는 기존 소비처 동작은 **유지**(회귀 없음).
- **FR-003**: 부분 라인 버퍼링·손상 라인 스킵 등 기존 파싱 동작은 **보존**.

## Success Criteria *(mandatory)*

- **SC-001**: 중간 `error`가 든 청크에서 그 **뒤 이벤트 유실 0**(시나리오 1).
- **SC-002**: 기존 스트림 소비처(분석·파싱) **회귀 0**(`complete` 종결·정상 종료 동작 유지).

## Assumptions

- 분석 스트림의 실제 종결은 연결 종료/`stream_end`. `error`는 데이터성(콘솔 표시).
- 현재 백엔드는 스트림 `error`를 종결 지점에서만 보냄 → 이 수정은 **잠재 결함의 방어적 교정**(현재 사용자 영향 0, 회귀 안전망). 정직히: 지금 보이는 버그를 고치는 게 아니라 파서 정확성을 맞춘다.
- 관련 별개 발견 **C(AFFECTS_TABLE 끝점=이름)** 는 **수정 불요**로 결론: AFFECTS_TABLE이 캔버스(HIDDEN_LINK_TYPES)·노드패널(EXCLUDED_RELS) 모두에서 숨김이라 이름-끝점 불일치가 **어떤 UI에도 영향 없음**, 가시 테이블 엣지(READS/WRITES)는 논리 fqn 사용으로 정상. (조사 결론, 코드 변경 없음.)
