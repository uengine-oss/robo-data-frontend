# Feature Specification: 스키마 탭 & 그래프 탐색 UI/UX 모던화 정합

**Feature Branch**: `045-schema-graph-nav-ux`

**Created**: 2026-06-29

**Status**: Draft

**Input**: User description: 스키마 탭(테이블 카드·상세패널·사이드바·검색)과 그래프 탭 노드검색(Overview)의 UI/UX를 일관·명확·모던하게 정합. 같은 의미는 어디서나 같은 색·위치·정렬, 마커는 의미가 읽히게, 잘 구현된 그래프 네비게이터/Overview를 기준으로. (이번 세션 실시간 피드백으로 적용한 변경의 사후 명세 + 미완 작업 SDD 포함.)

## 배경 한 줄

설계자(비개발자)가 스키마 탭에서 테이블을, 그래프 탭에서 코드 노드를 본다. 같은 의미(NOT NULL, 캔버스에 그려짐, 노드 종류)가 카드·상세패널·사이드바·검색마다 다른 색·위치·표현으로 나와 "이게 뭔지/뭐가 그려졌는지" 알기 어렵고 조잡했다. 잘 구현된 그래프 네비게이터/Overview를 기준으로 **일관성·정보전달·정렬**을 바로잡는다. 비개발자가 1차 사용자이므로 **논리명(한글 의미)을 우선** 보여준다.

## Clarifications

### Session 2026-06-29

- Q: 상단 전체검색의 목표 범위는? → A: **현재 탭 맥락 검색** — 그래프 탭이면 노드검색, 스키마 탭이면 테이블검색으로 라우팅하고 placeholder·동작이 현재 탭에 맞게 정직해야 한다. "All▾"·"⌘K"는 실제 동작에 연결하거나 제거(빈 장식 금지).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 테이블 카드가 정보를 일관·정렬되게 전달한다 (Priority: P1)

설계자가 스키마 캔버스의 테이블 카드를 보면, 각 컬럼의 이름·제약(기본키/외래키/필수)·타입이 **모든 행에서 일관된 위치로 정렬**되어 한눈에 읽힌다. "이 표시가 뭔지" 헷갈리지 않는다.

**Why this priority**: 카드는 스키마 탭의 핵심 표면. 정렬이 들쭉날쭉하거나 마커 의미가 안 읽히면 화면 전체가 조잡해 보인다.

**Independent Test**: 분석된 프로젝트에서 테이블을 캔버스에 올려, 컬럼이 많은/긴 이름/필수·키가 섞인 카드를 보고 정렬·표시가 일관된지 확인.

**Acceptance Scenarios**:

1. **Given** 한 컬럼이 NOT NULL일 때, **When** 카드를 보면, **Then** 그 컬럼에 "필수"를 뜻하는 마커가 **타입 바로 앞 일관된 위치**에 보이고, 그 의미를 범례에서 확인할 수 있다.
2. **Given** 컬럼명이 카드 폭보다 길 때, **When** 카드를 보면, **Then** 이름은 `…`로 말줄임되고 **제약·타입은 잘리지 않고 계속 보인다**.
3. **Given** 기본키/외래키 컬럼이 있을 때, **When** 카드를 보면, **Then** PK/FK가 텍스트로 표시되고 필수 마커·타입과 **세로로 정렬**된다(행마다 위치가 흔들리지 않는다).

---

### User Story 2 - 상세패널이 카드와 같은 규칙으로, 깔끔하게 보인다 (Priority: P1)

설계자가 테이블을 클릭해 상세패널을 열면, 컬럼 정보가 **카드와 같은 색·순서·정렬 규칙**으로 보이되, 큰 공간에 맞게 텍스트로 더 풍부하게(풀 타입, NOT NULL 텍스트) 표시된다. 영역 구분이 명확하고 잡다한 장식이 없다.

**Why this priority**: 같은 정보가 카드와 패널에서 다르게(색·순서·정렬) 보이면 신뢰가 깨진다(일관성).

**Independent Test**: 한 테이블의 카드와 상세패널을 나란히 비교해 NOT NULL 색·타입 위치·정렬이 일치하고, 컬럼 영역이 깔끔히 구분되는지 확인.

**Acceptance Scenarios**:

1. **Given** NOT NULL 컬럼이 있을 때, **When** 카드와 상세패널을 보면, **Then** 둘 다 **같은 색**으로 표시된다(카드=마커, 패널=텍스트로 형태만 다름).
2. **Given** 컬럼 목록을 볼 때, **When** 상세패널을 보면, **Then** 각 컬럼이 **배경으로 구분되는 단일 영역**으로 보이고 타입 표시가 **모든 행에서 같은 위치**에 정렬된다(지그재그 없음).

---

### User Story 3 - 캔버스에 이미 그려진 테이블이 명확히 구분되고, 컨트롤이 항상 있다 (Priority: P2)

설계자가 사이드바 목록에서 어떤 테이블이 **이미 캔버스에 그려졌는지** 한눈에 구분하고(그래프 네비게이터와 같은 방식), 논리/물리명 토글·비우기 같은 **캔버스 컨트롤은 캔버스가 비어 있어도 항상 같은 자리**에 있다.

**Why this priority**: "뭐가 그려졌는지 모르겠다", "토글이 사라진다"는 혼란을 없앤다.

**Independent Test**: 일부 테이블을 캔버스에 올린 뒤 사이드바에서 구분 표시를 확인하고, 캔버스를 비운 상태에서도 컨트롤이 보이는지 확인.

**Acceptance Scenarios**:

1. **Given** 일부 테이블이 캔버스에 있을 때, **When** 사이드바를 보면, **Then** 그 테이블은 **흐리게 + 초록 점이 행 맨 오른쪽**에 표시된다(그래프 네비게이터와 동일).
2. **Given** 캔버스가 비어 있을 때, **When** 스키마 탭을 보면, **Then** 논리/물리명 토글과 비우기 컨트롤이 **여전히 같은 자리에 보인다**(비우기는 비활성).

---

### User Story 4 - 그래프 노드검색이 "의미·소속·종류"로 읽히고 전체에 도달한다 (Priority: P2)

설계자가 그래프 Overview의 노드검색에 입력하면, 각 결과가 **논리명(한글 의미)을 우선**으로, 그 아래 **물리명·소속**(어느 테이블/모듈 소속인지)과 **종류 배지(실제 노드 색)**로 보인다. 결과가 많아도 **실제 개수**가 표시되고 **스크롤로 전부 도달**할 수 있다.

**Why this priority**: 비개발자가 코드 노드를 이름만으로는 이해 못 한다. 의미·소속이 핵심 가치이고, 결과 잘림은 신뢰를 떨어뜨린다.

**Independent Test**: "auth" 등으로 검색해 결과가 논리명 우선·소속 표시·종류 배지로 나오고, 10건 초과 시 실제 개수 표시 + 스크롤로 끝까지 도달하는지 확인.

**Acceptance Scenarios**:

1. **Given** 논리명이 있는 노드가 매칭될 때, **When** 검색하면, **Then** 결과 1차 줄은 **논리명**(없으면 물리명), 2차 줄은 **물리명·소속**(흐리게)로 보인다.
2. **Given** 노드 종류가 여럿(종류+역할 라벨)일 때, **When** 결과 배지를 보면, **Then** 배지는 **종류(자기 자신) 1개**만, 색은 **실제 캔버스 노드와 같은 색**이다.
3. **Given** 매칭 결과가 10건을 넘을 때, **When** 검색하면, **Then** 헤더에 **실제 전체 개수**가 표시되고 드롭다운을 **스크롤하면 끝 결과까지 도달**한다.
4. **Given** 이름/논리명/소속이 길 때, **When** 결과를 보면, **Then** 각 줄은 `…`로 말줄임되고 한 줄을 넘기지 않는다.

---

### User Story 5 - 스키마탭 검색이 그래프 검색과 일관된 톤으로 보인다 (Priority: P2)

설계자가 스키마탭 검색에 입력하면, 결과가 **그래프 Overview 검색과 같은 톤**(논리명 우선·소속·컴팩트·종류 표시)으로 세련되게 보인다. 이름 기반 검색과 **의미 기반 추천(semantic) 기능은 그대로 보존**된다.

**Why this priority**: 두 검색이 다른 톤(한쪽은 칙칙/조잡)이면 일관성이 깨진다. 단 기존 기능(의미검색)은 삭제 금지.

**Independent Test**: 스키마탭에서 검색해 결과가 그래프 검색과 같은 표현(논리명 우선·소속·컴팩트)인지, 의미검색 섹션이 여전히 동작/표시되는지 확인.

**Acceptance Scenarios**:

1. **Given** 검색어를 입력할 때, **When** 스키마탭 검색결과를 보면, **Then** 각 결과가 **논리명 우선 + 소속(스키마) + 컴팩트 행**으로 보이고, 과거의 칙칙한 표현이 없다.
2. **Given** 의미 기반 추천이 있을 때, **When** 검색하면, **Then** **의미검색 섹션이 보존**되어 표시된다(키 미설정 등은 정직하게 안내).

---

### User Story 6 - 상단 전체검색이 정직하고 완전하게 동작한다 (Priority: P3)

설계자가 화면 상단 전체검색을 쓰면, **안내 문구(placeholder)와 실제 동작이 일치**하고, 약속한 범위를 실제로 검색하며, 동작하지 않는 장식이 없다.

**Why this priority**: 현재 안내는 "클래스·메서드·테이블·패키지 검색"이라 적혀 있으나 실제론 키워드를 스키마 탭으로만 보내고, "All▾"·"⌘K"는 동작이 없다(정직성 위반, 헌법 IV).

**Independent Test**: 상단 검색에 키워드를 입력해 안내대로 동작하는지, 장식 요소가 정리/연결되었는지 확인.

**Acceptance Scenarios**:

1. **Given** 상단 검색에 입력할 때, **When** 검색하면, **Then** **현재 탭에 맞는 검색**(그래프 탭=노드검색, 스키마 탭=테이블검색)으로 동작하고 **안내 문구가 그 동작과 일치**한다(거짓 표기 없음).
2. **Given** 동작하지 않는 컨트롤("All▾"·"⌘K")이 있을 때, **When** 정리 후 보면, **Then** 실제 동작에 연결되거나 제거되어 **빈 장식이 남지 않는다**.

> 전체검색의 **목표 범위 = 현재 탭 맥락 검색**으로 확정(Clarifications 2026-06-29). 그래프 탭=노드검색, 스키마 탭=테이블검색으로 라우팅. FR-018 참조.

---

### Edge Cases

- 컬럼명·논리명·소속이 매우 길 때: 각 필드를 `…`로 말줄임하고 한 줄을 유지한다(겹침·줄바꿈 금지).
- 한 컬럼이 PK이면서 NOT NULL일 때: PK/FK 표시와 필수 마커가 **각자 자리에서 동시에** 보이되 겹치지 않는다.
- 노드/테이블에 논리명이 없을 때: 물리명으로 폴백한다(빈 줄을 만들지 않는다).
- 노드 소속을 식별자에서 못 구할 때(소속 없는 최상위): 소속 줄을 생략한다(가짜로 채우지 않는다).
- 검색 매칭이 0건일 때: "없음"을 정직하게 안내한다.
- 의미검색이 환경상 불가(키 미설정)할 때: 기능을 삭제하지 않고 그 사유를 정직하게 안내한다.

## Requirements *(mandatory)*

### Functional Requirements

**테이블 카드 (US1)**

- **FR-001**: 카드 컬럼 행은 이름·제약(PK/FK·필수)·타입을 **행마다 일관된 위치**로 정렬해야 한다(특정 항목 유무로 다른 항목의 가로 위치가 흔들리지 않아야 한다).
- **FR-002**: NOT NULL(필수)은 **눈에 띄는 마커**로 표시하고, 그 의미를 **범례로 설명**해야 한다(마커만 보고 뜻을 모르는 상태 금지).
- **FR-003**: PK/FK는 텍스트로 표시하고, 타입은 **행 맨 오른쪽 고정 위치**에 둔다.
- **FR-004**: 컬럼명이 카드 폭을 넘으면 이름을 말줄임하고, 제약·타입은 **항상 보이게** 유지해야 한다.

**상세패널 (US2)**

- **FR-005**: 상세패널의 컬럼 표시는 카드와 **같은 색·순서 규칙**을 따라야 한다(같은 의미=같은 색). 형태는 맥락에 맞게 다를 수 있다(카드=마커, 패널=텍스트).
- **FR-006**: 상세패널의 타입·NOT NULL은 **모든 행에서 같은 위치**에 정렬되어야 한다(지그재그 금지).
- **FR-007**: 상세패널의 각 컬럼은 **배경으로 구분되는 단일 영역**으로 보이고, 불필요한 이중 박스·강조선 등 장식을 두지 않는다.

**사이드바 & 컨트롤 (US3)**

- **FR-008**: 사이드바에서 **캔버스에 이미 그려진** 테이블은 그래프 네비게이터와 **동일한 방식**(흐림 + 초록 점이 행 맨 오른쪽)으로 구분 표시해야 한다.
- **FR-009**: 캔버스 컨트롤(논리/물리명 토글, 비우기)은 **캔버스 노드 유무와 무관하게 항상 같은 자리**에 표시되어야 한다(비울 게 없으면 비우기는 비활성).

**그래프 노드검색 (US4)**

- **FR-010**: 노드검색 결과는 **논리명을 1차**로(없으면 물리명), **물리명·소속을 2차**로 표시해야 한다.
- **FR-011**: 결과의 **소속**(어느 테이블/모듈에 속하는지)을 함께 보여줘야 한다.
- **FR-012**: 결과 배지는 노드의 **종류(자기 자신 라벨) 1개**만 표시하고, 색은 **실제 캔버스 노드 색과 동일**해야 한다.
- **FR-013**: 검색 결과 개수는 **실제 전체 개수**를 표시하고(임의 상한 표기 금지), 모든 결과에 **스크롤로 도달**할 수 있어야 한다.
- **FR-014**: 각 결과의 이름·논리명·소속은 길면 말줄임하고 한 줄을 유지해야 한다.

**스키마탭 검색 (US5)**

- **FR-015**: 스키마탭 검색결과는 그래프 노드검색과 **같은 톤**(논리명 우선·소속·컴팩트·종류 표시)으로 표시해야 한다.
- **FR-016**: 이름 기반 검색과 **의미 기반 추천(semantic) 기능을 보존**해야 한다(삭제 금지). 의미검색이 환경상 불가하면 사유를 정직하게 안내한다.

**상단 전체검색 (US6)**

- **FR-017**: 상단 전체검색은 **안내 문구와 실제 동작이 일치**해야 하며, 동작하지 않는 장식 컨트롤을 남기지 않는다(실제 동작에 연결하거나 제거).
- **FR-018**: 상단 전체검색은 **현재 탭 맥락 검색**으로 동작해야 한다 — 그래프 탭이면 노드검색, 스키마 탭이면 테이블검색으로 라우팅하고, placeholder·동작이 **현재 탭에 맞게** 정직해야 한다(고정된 거짓 안내 금지).

**횡단 (모든 표면)**

- **FR-019**: 같은 의미(NOT NULL, 캔버스에 그려짐, 노드 종류·소속)는 **카드·상세패널·사이드바·검색 어디서나 같은 색·위치·표현 규칙**을 따라야 한다.
- **FR-020**: 정렬·간격은 **레이아웃이 계산되는 방식**(상대단위·정렬규칙)으로 잡아 매직 픽셀 눈대중을 쓰지 않으며, 다른 화면 크기·임베드에서도 유지되어야 한다.

### Key Entities *(include if feature involves data)*

- **테이블 컬럼(Column)**: 이름(물리명)·논리명·타입·제약(기본키/외래키/필수=NOT NULL)·소속 테이블을 가진다. 카드·상세패널·검색의 표시 단위.
- **그래프 노드(Node)**: 종류(자기 자신 라벨)·역할(부가 라벨)·논리명·물리명·소속(식별자 계층의 부모)을 가진다. 검색 결과·캔버스의 표시 단위. 색은 종류로 결정된다.
- **검색 결과 항목(Search result)**: 한 노드/테이블에 대한 표시 = 종류 배지 + 1차(논리명) + 2차(물리명·소속). 카드·패널과 같은 의미·색 규칙을 공유한다.
- **캔버스 상태(On-canvas)**: 어떤 노드/테이블이 현재 캔버스에 올라가 있는지. 사이드바·검색에서 동일하게 구분 표시된다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 한 테이블 카드의 모든 컬럼 행에서 제약·필수 마커·타입의 가로 위치가 **항상 같다**(행 간 위치 불일치 0건).
- **SC-002**: 같은 의미(NOT NULL 등)가 카드·상세패널에서 **같은 색**으로 보인다(색 불일치 0건).
- **SC-003**: 새 사용자가 안내 없이도 사이드바에서 "어떤 테이블이 캔버스에 있는지" **즉시 구분**할 수 있다.
- **SC-004**: 노드/테이블 검색 결과에서 비개발자가 **논리명만 보고 5초 안에** 무엇인지 이해하고, 어디에 속하는지(소속) 함께 확인할 수 있다.
- **SC-005**: 검색 결과가 N건일 때 화면에 **N(실제 개수)**가 표시되고, 사용자가 **마지막 결과까지 도달**할 수 있다(잘림 0건).
- **SC-006**: 그래프 검색과 스키마탭 검색의 결과 표현이 **동일한 형태**다(톤 불일치 0건). 의미검색 기능은 **계속 동작/표시**된다(기능 손실 0건).
- **SC-007**: 상단 전체검색의 안내 문구가 실제 동작과 일치하고, **동작 없는 장식이 0개**다.

## Assumptions

- 1차 사용자는 **비개발자 설계자** — 그래서 모든 표면에서 **논리명(한글 의미)을 우선** 보여준다.
- 노드의 **소속은 식별자(id) 계층**에 인코딩되어 있다(예: `테이블.컬럼`, `패키지.모듈.함수`) — 별도 관계 조회 없이 파생 가능. (식별자 통일 = analyzer spec 017.)
- 캔버스 노드 색은 **종류(labels[0]) 기준** 단일색이다(spec 033/035 위치 계약) — 검색 배지도 같은 색을 쓴다.
- 잘 구현된 **그래프 네비게이터/Overview**가 일관성의 기준 컴포넌트다.
- 기존 **의미검색(semantic) API·동작은 변경 없이 보존**한다(표시만 정리).
- 이 기능은 기존 분석 그래프·카탈로그 스키마 데이터를 전제로 하며 새 백엔드 계약을 요구하지 않는다(표시 계층 변경).

## Dependencies *(boundary)*

- **공유 계약 변경 없음**: 카탈로그/그래프 응답 스키마·게이트웨이 라우트를 바꾸지 않는다(표시 계층 한정). 따라서 다른 서비스에 전파되는 contract 변경은 없다.
- **전제 데이터**: 테이블 `logical_name`(catalog), 노드 `logical_name`/식별자 계층(analyzer 그래프), 의미검색 엔드포인트(존재 시).
