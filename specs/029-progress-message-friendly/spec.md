# Feature Specification: 분석 진행 메시지 친절화 (종류·이름·동작 + 전략별 라이브)

**Feature Branch**: `029-progress-message-friendly`

**Created**: 2026-06-27

**Status**: Draft

**Input**: User description: 분석 진행 화면의 콘솔 진행 메시지가 "코드 N개째 분석 중"처럼 불친절하다. 무엇을(대상) 어떻게(작업) 분석 중인지 알려야 하고, dbms 전략에선 진행 메시지가 아예 안 뜨는 문제, 'Component' 미매핑("항목")·죽은 'Question' 매핑을 함께 바로잡는다.

## 배경 / 현재 동작 (왜 필요한가)

소스 폴더를 분석하면 진행 화면에 **콘솔 진행 메시지**가 줄글로 흐른다(7단계 패널·진행바와 별개 채널). 현재 이 메시지는 `🧠 코드 3개째 분석 중`처럼 **종류와 개수만** 보여 준다. 사용자(분석 결과를 보는 비개발자) 피드백:

1. **불친절** — "코드 몇 개"만으로는 지금 **무엇을** 들여다보는지, **어떻게** 처리 중인지 알 수 없다.
2. **dbms 무음** — dbms 전략은 분석을 묶음(Batch) 단위로 돌고, 화면이 이 묶음 진행을 **건너뛰어** 가장 긴 분석 구간 내내 메시지가 한 줄도 안 뜬다(멈춘 듯 보임).
3. **맹맹한 라벨** — 막바지 '구성요소' 처리는 종류 이름이 빠져 `🧠 항목 N개째`로 뜬다. 반대로 화면엔 '질문' 종류 매핑이 있으나 실제로는 그 종류가 오지 않는다(죽은 매핑).

**확인된 사실(실데이터·코드 근거)**:
- 진행 신호(processing_event)는 처리 대상의 **식별자만** 담고 이름은 안 담는다. 그러나 그 대상(함수·테이블·모듈)은 **앞 단계에서 이미 라이브 그래프에 이름표를 달고 그려져** 있어, 식별자로 **이름과 종류(라벨)를 되찾을 수 있다**(framework 실분석 로그로 검증: 함수 38개가 먼저 그려진 뒤 처리됨).
- framework는 **함수 1개 단위**, dbms는 **형제 묶음 1개 단위**로 처리하며 두 방식은 **전략상 동시에 일어나지 않는다**. dbms 묶음의 식별자는 보통 **상위 루틴(프로시저 등)** 을 가리켜 이름이 있다(이름 없는 중첩 묶음만 예외).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 무엇을·어떻게 분석 중인지 보인다 (Priority: P1)

분석을 실행한 사용자가 진행 화면을 보면, 콘솔에 **종류 + 지금까지 처리한 개수 + 그 단계에 맞는 작업 + 방금 처리한 대상 이름**이 한국어로 흐른다. 예: `🧠 함수 12개 분석 중 — 'a000_input_validation'`, `🗂️ 테이블 7개 설명 채우는 중 — 'zord_acnt'`.

> 형식: `{종류} {개수}{단위} {동작} — '{현재 이름}'`. 개수는 진행감(멈춤 아님)을, 이름은 "지금 무엇"을 전한다. 이름을 못 찾으면 이름 부분은 생략.

**Why this priority**: 진행 화면의 핵심 가치(=멈추지 않고 무엇을·얼마나 하는지 안심시키는 것)를 직접 전달한다. 단독으로도 체감 개선이 가장 크다.

**Independent Test**: framework 소스를 분석하는 동안(또는 실분석 로그/스트림 주입으로) 콘솔에 처리 개수가 단조 증가하며, 실제 함수·테이블 이름이 단계별 작업 문구와 함께 표시되는지 확인.

**Acceptance Scenarios**:

1. **Given** framework 분석이 코드 분석 단계를 지나는 중, **When** 함수 처리가 진행됨, **Then** 콘솔에 `함수 N개 분석 중 — '<실제 함수명>'`이 뜨고 N이 단조 증가한다.
2. **Given** 후처리 단계에서 테이블 설명을 채우는 중, **When** 테이블 처리가 진행됨, **Then** `테이블 N개 설명 채우는 중 — '<실제 테이블명>'`이 뜬다.
3. **Given** 방금 처리한 대상의 이름을 라이브 그래프에서 못 찾는 경우, **When** 그 대상이 처리됨, **Then** 이름 부분 없이 **종류 + 개수 + 작업**만 자연스러운 문장으로 뜬다(예: `구성요소 2개 묶는 중`).

---

### User Story 2 - dbms 분석도 진행 메시지가 뜬다 (Priority: P1)

dbms 전략으로 분석할 때도, **묶음(Batch) 처리 건수**가 늘 때마다 진행 메시지가 흐른다(예: `🧠 코드 묶음 12건 분석 중 — 'PRC_PAY_AUTH'`). 더 이상 가장 긴 구간이 무음이 아니다. dbms는 작업 단위가 함수 1개가 아니라 형제 묶음 1개라서, **개수의 단위가 "건"(배치 수)** 이다.

**Why this priority**: 현재 dbms는 이 화면이 통째로 비어 "멈춘 것처럼" 보이는 명백한 공백이다. 전략 간 동등성 확보.

**Independent Test**: dbms 묶음(Batch) 처리 신호가 들어올 때 메시지가 뜨고(무음 아님), 처리 건수가 단조 증가하며, 방금 묶음의 대상 이름이 라이브 그래프에 있으면 이름이 붙는지 확인. (현재 dbms 코드분석 실데이터가 없어 라이브 실증 불가 → 신호 주입/로직 단위로 검증하고, 라이브 실증은 dbms 소스 확보 시로 명시.)

**Acceptance Scenarios**:

1. **Given** dbms 분석이 코드 분석 단계 진행 중, **When** 한 묶음 처리가 끝남, **Then** 콘솔에 `코드 묶음 N건 분석 중`이 뜬다(무음이 아님, N 단조 증가).
2. **Given** 방금 묶음의 대상 이름을 라이브 그래프에서 찾음, **When** 그 묶음이 처리됨, **Then** 메시지 끝에 `— '<이름>'`이 붙는다.
3. **Given** 방금 묶음의 대상 이름이 없음, **When** 처리됨, **Then** 이름 부분 없이 `코드 묶음 N건 분석 중`만 뜬다.

---

### User Story 3 - 진행 개수가 끊김 없이 한 줄기로 증가 (Priority: P2)

진행 메시지의 흐름이 처리 대상별로 **중복 없이, 단조 증가**한다. 한 분석에서 진행 개수가 두 갈래로 갈라져 "리셋된 것처럼" 보이지 않는다.

**Why this priority**: 과거 사용자 피드백("리셋처럼 보임")의 근본 원인 제거. P1만으로도 가치 있으나 흐름 품질을 완성한다.

**Independent Test**: framework·dbms 각각에서 같은 대상이 여러 번 신호를 보내도 한 번만 세고, 종류별 빈도 조절(플러드 방지)이 유지되는지 확인.

**Acceptance Scenarios**:

1. **Given** 한 대상이 여러 세부 작업 신호로 여러 번 옴, **When** 처리됨, **Then** 진행 개수는 그 대상에 대해 1회만 증가한다.
2. **Given** 코드 처리 신호가 전략에 따라 함수 단위 또는 묶음 단위로 옴, **When** 진행됨, **Then** 둘은 동일한 "코드" 진행 줄기로 합산되어 끊김 없이 증가한다.

---

### Edge Cases

- 처리 대상 식별자가 비어 있으면 → 그 신호는 메시지/카운트에서 제외(현행 유지).
- 라이브 그래프에 아직 대상 노드가 없으면 → 이름 생략하고 종류+작업만(US1-3).
- 알 수 없는 단계 문자열이면 → 일반 작업 문구("처리하고 있어요")로 폴백(역행·오류 없이).
- 처리 시작/실패 신호 → 메시지 카운트 대상 아님(완료 신호만 셈, 현행 유지).
- 단계 라이브 전진(spec 028) 동작은 이 변경의 영향을 받지 않는다(같은 핸들러 맨 앞 블록 보존).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 진행 메시지는 **종류(한국어) + 지금까지 처리한 개수(단위 포함) + 그 단계에 맞는 작업 문구 + 방금 처리한 대상 이름(있을 때)** 으로 구성되어야 한다. 형식: `{종류} {개수}{단위} {동작} — '{이름}'`.
- **FR-002**: 대상 이름과 종류는 **처리 신호의 식별자로 라이브 그래프에서 그 대상 노드를 찾아** 그 노드의 표시 이름과 종류(라벨)에서 가져와야 한다. 노드를 못 찾으면 이름은 생략한다.
- **FR-003**: 종류(한국어)는 **노드의 실제 종류(라벨)** 기반이어야 하며 framework·dbms 어느 전략이든 동작해야 한다(예: 함수/프로시저/트리거/모듈/테이블/구성요소). 라벨로 판별 불가 시 처리 신호의 종류값으로 폴백한다.
- **FR-004**: 작업 문구는 **현재 단계**에서 파생되어야 한다(맥락 구성=요점 살펴봄, 코드 분석=의미 분석, 모듈 사전분석=미리 살펴봄, 모듈 요약=요약, 테이블 설명 보강=설명 채움, 구성요소=묶음). 미등록 단계는 일반 작업 문구로 폴백한다.
- **FR-005**: dbms 전략의 **묶음(Batch) 처리 신호를 건너뛰지 말아야 한다**. 묶음 신호도 진행 메시지·카운트 대상이며, 식별자(상위 대상)로 이름을 조회해 표시한다.
- **FR-006**: 코드 처리 진행 개수는 **단일 "코드" 줄기로 단조 증가**해야 한다(0으로 리셋·감소 금지). 단위는 전략을 따른다: framework=처리한 **함수 개수**, dbms=처리한 **묶음(배치) 건수**. 두 전략은 동시에 발생하지 않으므로 한 분석에서는 한 단위만 쓰인다.
- **FR-007**: framework는 같은 함수가 여러 세부 신호로 와도 **그 함수를 1회만** 센다(중복 제거). dbms는 **묶음마다 1건** 센다. 모든 종류에 **빈도 조절(플러드 방지)** 을 적용해 메시지가 도배되지 않아야 한다.
- **FR-008**: '구성요소' 종류에 한국어 라벨과 빈도 조절 값이 있어야 한다(맹맹한 "항목" 제거).
- **FR-009**: 실제로 발생하지 않는 종류 매핑('질문')과 문서의 미사용 종류 표기('Split')를 정리해야 한다(죽은 코드/문서 드리프트 제거).
- **FR-010**: **완료 신호만** 메시지·카운트 대상이며, 처리 대상의 원시 식별자는 사용자에게 노출하지 않는다(현행 보존).
- **FR-011**: 단계 라이브 전진(spec 028) 동작은 보존되어야 한다(이 변경으로 회귀 없음).

### Key Entities

- **처리 신호(progress signal)**: 한 처리 단위의 진행을 나타냄. 단계, 종류, 대상 식별자, 세부 작업, 상태(시작/완료/실패)를 가짐. 이름은 담지 않음.
- **라이브 그래프 노드**: 분석 중 화면에 그려지는 대상(함수·테이블·모듈·프로시저 등). 표시 이름과 종류(라벨)를 가지며, 처리 신호의 식별자로 조회 가능.
- **진행 메시지**: 사용자에게 보이는 한 줄 한국어 문장(종류+이름+작업). 카운트는 종류별 중복 제거 집합으로 관리.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: framework 분석 중 콘솔 진행 메시지의 **100%가 종류와 단계별 작업 문구**를 포함하며, 대상 노드가 라이브 그래프에 있는 경우 **실제 이름**을 포함한다.
- **SC-002**: dbms 처리 신호가 들어오는 동안 진행 메시지가 **0줄이 아니다**(현재=0줄 → 개선 후 매 묶음 진행 시 표시).
- **SC-003**: 한 분석 동안 "코드" 진행 개수가 **감소하거나 0으로 리셋되는 일이 없다**(단조 증가).
- **SC-004**: '항목'으로 표기되던 구성요소 처리가 **고유한 한국어 종류명**으로 표시되고, 발생하지 않는 종류명은 화면 어디에도 나타나지 않는다.
- **SC-005**: 단계 패널의 라이브 전진(spec 028) 동작이 **변경 전과 동일**하게 유지된다(회귀 0).

## Assumptions

- 사용자는 분석 결과를 보는 비개발자에 가깝고, 진행 화면의 목적은 "멈추지 않고 무엇을 하는지" 안심시키는 것이다.
- framework는 neo4j DB 재분석 실데이터로 라이브 검증 가능하다. **dbms는 현재 코드분석 노드 데이터가 없어(test DB=스키마만)** 라이브 실증 불가 → dbms 동작은 신호 주입/로직 수준으로 검증하고, 라이브 실증은 dbms 소스 확보 시로 명시한다.
- 처리 대상 노드는 처리 신호보다 **먼저** 라이브 그래프에 그려진다(앞 단계의 노드 스트림). 이름 조회는 이 순서에 의존한다.
- 이 스펙은 spec 028(단계 라이브 전진, 구현·검증됨)과 같은 화면이나 **별개 관심사(콘솔 메시지)** 다. 진행바 % 라이브화·R/W 대상 끝점 정합·스트림 오류 절단은 각각 별도 스펙으로 다룬다.
