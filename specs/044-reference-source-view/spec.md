# Feature Specification: 스키마 탭 참조 UX 근본 재설계 + 컨트롤 배치 일관화

**Feature Branch**: `044-reference-source-view`

**Created**: 2026-06-28

**Status**: Draft

**Input**: User description: 스키마 탭의 (1) "참조 열기"(테이블 출처/참조 → 소스 코드 패널)를 파일 전체가 아니라 관련 그래프 노드의 원문 코드(해당 함수/프로시저 범위)만 + 접근 지점(줄) 강조로 근본 재설계하고, (2) 참조 진입점(트리거) 발견성을 개선하며, (3) "참조 없음"과 "불러오기 실패"를 구분하고, (4) "테이블 보기" 등 스키마 탭 컨트롤을 그래프 탭처럼 캔버스 위 floating으로 일관 배치한다.

## 배경 한 줄

설계자(비개발자)가 스키마 탭에서 테이블을 보다가 "이 테이블, 코드 어디서 쓰지?"를 누르면 — 지금은 **파일 전체**가 통째로 뜨고 한 줄만 칠해진다. 이걸 "**그 테이블을 만지는 함수의 코드만, 만지는 그 줄을 강조해서**" 보여주는 것으로 근본 교체한다. 필요한 데이터(함수의 시작/끝 줄, 테이블을 접근한 정확한 줄)는 분석 그래프에 이미 다 들어 있다 — 화면이 안 쓰고 있을 뿐이다. 더불어 스키마 탭의 캔버스 컨트롤(참조 진입점·"테이블 보기" 등)이 **그래프 탭은 캔버스 위 floating인데 스키마 탭만 좌측 패널 바닥(탐색기 푸터)에 박혀** 일관성이 깨진 것을 함께 바로잡는다.

## Clarifications

### Session 2026-06-28

- Q: US4 컨트롤 일관화 범위는? → A: 스키마 탭 캔버스 컨트롤 전반("테이블 보기" + 논리/물리명 토글 + 범례)을 그래프 탭식 캔버스 위 floating 그룹으로 일관 정리(todo의 DRY 잔여 포함).
- Q: 한 함수가 한 테이블을 여러 줄에서 접근할 때 참조 목록 표현은? → A: 접근 지점별 N행(같은 함수라도 읽고/쓰는 줄마다 목록 항목 1개, 클릭하면 그 줄로).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 참조를 열면 "그 함수의 코드 + 만지는 줄"만 보인다 (Priority: P1)

설계자가 한 테이블의 참조 목록에서 항목 하나를 고르면, 코드 패널에 **그 함수(또는 프로시저)의 코드만** 뜨고, 그 함수 안에서 **이 테이블을 읽거나 쓴 정확한 줄이 강조**되어 "여기서 이 테이블을 참조함"이 한눈에 보인다. 파일 전체를 스크롤하며 찾을 필요가 없다.

**Why this priority**: 이 기능의 본질 가치. "코드를 못 읽는 설계자가, 코드를 읽지 않고도 테이블이 어디서 어떻게 쓰이는지 본다"가 이 화면의 존재 이유다. 파일 전체 덤프는 그 가치를 흐린다.

**Independent Test**: 분석된 프로젝트(예: zapamcom)에서 한 테이블을 캔버스에 올리고 참조 항목을 클릭 → 코드 패널이 해당 함수의 라인 범위만 표시하고, 강조된 줄이 실제로 그 테이블을 읽/쓰는 줄인지 원문과 대조해 확인.

**Acceptance Scenarios**:

1. **Given** 한 함수가 어떤 테이블을 읽는(또는 쓰는) 것으로 분석돼 있고 그 함수의 시작·끝 줄과 접근 줄이 그래프에 있을 때, **When** 그 테이블의 참조 목록에서 해당 함수 항목을 클릭하면, **Then** 코드 패널은 그 함수의 시작~끝 줄 범위 코드만 보여주고 접근 줄을 강조한다.
2. **Given** 프레임워크 전략으로 분석된 함수 참조와 DBMS 전략으로 분석된 프로시저 참조가 둘 다 있을 때, **When** 각각을 열면, **Then** 두 경우 모두 "해당 루틴 범위 코드 + 접근 줄 강조"로 **동일하게** 동작한다(한쪽만 파일 전체로 뜨지 않는다).
3. **Given** 강조된 줄이 패널의 보이는 영역 밖에 있을 때, **When** 참조를 열면, **Then** 강조 줄이 보이도록 자동으로 스크롤된다.

---

### User Story 2 - 어디를 눌러야 하는지 분명하다 (Priority: P2)

설계자가 테이블에서 "코드 참조 보기"로 들어가는 입구가 한눈에 보이고, 논리명/물리명 어느 모드에서도 같은 자리에서 접근할 수 있다. 작은 색칩을 우연히 눌러야 알게 되는 일이 없다.

**Why this priority**: 지금 입구가 아주 작은 색칩이고 한 모드에서만 나타나, "어디를 눌러야 하나 / 눌러도 반응이 없다"는 혼란을 만든다. P1의 가치를 실제로 닿게 해주는 통로다.

**Independent Test**: 테이블 노드를 논리명 모드와 물리명 모드 양쪽에서 보고, 참조 진입점이 두 모드 모두에서 발견 가능한 위치에 일관되게 있는지, 참조가 있는 테이블에서 명확히 클릭 가능한지 확인.

**Acceptance Scenarios**:

1. **Given** 한 테이블에 참조가 있을 때, **When** 그 테이블 노드를 보면, **Then** 참조를 열 수 있는 입구가 노드의 다른 동작들과 조화로운 위치에 분명하게(과하게 튀지 않게) 보인다.
2. **Given** 사용자가 논리명 모드로 보고 있을 때, **When** 같은 테이블을 보면, **Then** 참조 입구가 물리명 모드와 동일하게 접근 가능하다.

---

### User Story 3 - "참조 없음"과 "불러오기 실패"가 구분된다 (Priority: P3)

참조를 열었을 때 결과가 비어 있으면, 그게 "참조가 정말 없음"인지 "불러오다 실패함"인지 사용자에게 정직하게 구분해 알리고, 실패면 다시 시도할 수 있다.

**Why this priority**: 지금은 둘 다 조용히 빈 화면이라 신뢰를 떨어뜨린다. 데이터 정직성(헌법 IV) 원칙.

**Independent Test**: 참조가 없는 테이블, 그리고 백엔드 응답이 실패하는 상황을 각각 만들어, 안내 문구가 서로 다르고 실패 시 재시도가 제공되는지 확인.

**Acceptance Scenarios**:

1. **Given** 어떤 테이블에 참조가 하나도 없을 때, **When** 참조를 열면, **Then** "참조 없음"이라는 안내가 보인다.
2. **Given** 참조를 불러오다 실패했을 때, **When** 그 결과를 보면, **Then** 실패임을 알리고 다시 시도할 수단이 제공된다(빈 목록으로 위장하지 않는다).

---

### User Story 4 - 스키마 탭 컨트롤이 그래프 탭과 일관되게 놓인다 (Priority: P2)

설계자가 스키마 탭의 캔버스 컨트롤 전반("테이블 보기"로 테이블을 캔버스에 올리는 입구, 논리명/물리명 토글, 범례)을 그래프 탭과 **같은 자리·같은 방식**(캔버스 위에 떠 있는 컨트롤 그룹)에서 쓴다. 한 탭에서는 캔버스 위에 있고 다른 탭에서는 좌측 목록 패널 맨 아래에 박혀 있어 헷갈리는 일이 없다.

**Why this priority**: 두 탭을 오가는 사용자가 매번 컨트롤을 다른 곳에서 찾아야 하는 불일치를 없앤다. 참조 트리거(US2)와 같은 "스키마 탭 컨트롤을 그래프 탭 기준으로 일관 배치" 뿌리다.

**Independent Test**: 그래프 탭과 스키마 탭을 나란히 비교해, 캔버스 컨트롤이 동일한 영역(캔버스 위 floating)에 일관되게 위치하는지, "테이블 보기"가 좌측 패널 바닥이 아니라 캔버스 위에서 접근되는지 확인.

**Acceptance Scenarios**:

1. **Given** 사용자가 그래프 탭에서 캔버스 위 floating 컨트롤로 보기를 조작해봤을 때, **When** 스키마 탭으로 전환하면, **Then** 스키마 탭의 캔버스 컨트롤("테이블 보기" 등)도 캔버스 위 동일한 영역에서 동일한 방식으로 보인다.
2. **Given** 스키마 탭을 볼 때, **When** "테이블 보기" 입구를 찾으면, **Then** 좌측 목록 패널 바닥(탐색기 푸터)이 아니라 캔버스 위에 있다.

---

### Edge Cases

- 함수의 시작/끝 줄이나 접근 줄 정보가 그래프에 없을 때: 가능한 만큼만 보여주되(예: 범위 정보 없으면 그 함수의 시작 줄을 기준으로), 가짜 코드를 만들지 않는다.
- 분석 당시의 원본 소스가 디스크에 더는 없을 때: 파일 전체든 일부든 가짜로 채우지 않고 "원본 소스를 찾을 수 없음"을 정직하게 안내한다(기존 동작 유지).
- 같은 테이블을 한 함수가 여러 줄에서 만질 때: 참조 목록에 **접근 지점(줄)마다 별도 항목**으로 나오고, 항목을 고르면 그 함수 코드 범위에서 **그 지점 줄**이 강조된다.
- 강조할 접근 줄이 함수 범위 밖으로 잘못 가리킬 때: 범위 안으로 보정하거나 강조를 생략하되 패널이 깨지지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 참조 항목을 열면, 시스템은 **그 참조에 해당하는 코드 노드(함수/프로시저/메서드)의 코드 범위만** 코드 패널에 보여줘야 한다(파일 전체 표시 금지).
- **FR-002**: 시스템은 그 코드 안에서 **해당 테이블을 읽거나 쓴 정확한 지점(줄)을 강조**해야 한다.
- **FR-003**: 시스템은 프레임워크 전략 참조와 DBMS 전략 참조를 **동일한 방식**(해당 루틴 범위 + 접근 줄 강조)으로 표시해야 한다.
- **FR-004**: 강조 지점이 보이지 않는 위치면, 시스템은 그 지점이 보이도록 자동 스크롤해야 한다.
- **FR-005**: 참조를 여는 입구(트리거)는 **참조가 있는 테이블에서 발견 가능한 위치**에 있어야 하며, **논리명/물리명 모드와 무관하게** 동일하게 접근 가능해야 한다.
- **FR-006**: 시스템은 "참조 없음"과 "불러오기 실패"를 **구분된 안내**로 표시해야 하며, 실패 시 **재시도 수단**을 제공해야 한다(조용히 빈 화면으로 위장 금지).
- **FR-007**: 원본 소스를 찾을 수 없으면, 시스템은 가짜 코드를 만들지 않고 **정직한 빈 상태**를 보여줘야 한다.
- **FR-008**: 코드 패널은 표시 중인 코드가 **어느 함수/프로시저의 어느 줄 범위**인지(루틴 이름·강조 줄 번호)를 사용자에게 명시해야 한다.
- **FR-009**: 스키마 탭의 캔버스 컨트롤 전반("테이블 보기" 입구, 논리명/물리명 토글, 범례)은 그래프 탭과 **동일한 영역(캔버스 위 floating)·동일한 상호작용 방식**의 컨트롤 그룹으로 배치되어야 한다(좌측 목록 패널 바닥에 배치 금지). 중복 마크업(논리/물리명 토글 등)은 단일 컴포넌트로 합쳐 DRY를 지킨다.
- **FR-010**: 컨트롤의 정렬·간격은 매직 픽셀 눈대중이 아니라 **레이아웃이 계산되는 방식**(정렬/간격 규칙·상대단위)으로 잡아 다른 화면 크기·임베드에서도 유지되어야 한다.

### Key Entities *(include if feature involves data)*

- **참조(Reference)**: "어떤 코드가 이 테이블을 **이 줄에서** 읽거나 쓴다"는 사실 1건 = **접근 지점 단위**. 가리키는 코드 노드, 접근 종류(읽기/쓰기/참조), **접근한 정확한 줄**을 가진다. 같은 함수가 여러 줄에서 만지면 줄마다 별개 참조다.
- **코드 노드(Code node)**: 함수/프로시저/메서드 등 호출 가능한 단위. 자기 코드의 **시작 줄과 끝 줄**을 안다(코드 범위의 진실).
- **접근 지점(Access point)**: 코드 노드 안에서 그 테이블을 실제로 만진 줄. 강조의 기준.
- **코드 패널(Source panel)**: 선택한 참조의 코드 범위를 표시하고 접근 지점을 강조하는 우측 화면.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 설계자가 참조를 열었을 때, 화면에 보이는 코드는 **해당 함수/프로시저 1개 범위**이며 파일 전체가 아니다(100% 케이스).
- **SC-002**: 참조를 연 직후 **강조된 줄이 보이는 영역 안**에 있어, 사용자가 추가 스크롤 없이 접근 지점을 즉시 확인할 수 있다.
- **SC-003**: 프레임워크 참조와 DBMS 참조가 **동일한 표시 형태**를 보인다(둘 중 하나가 파일 전체로 뜨는 비대칭 0건).
- **SC-004**: 새 사용자가 안내 없이도 테이블에서 "코드 참조 보기" 입구를 **5초 안에** 찾을 수 있다(논리명·물리명 양쪽).
- **SC-005**: 참조 결과가 빈 경우, 사용자가 그것이 "없음"인지 "실패"인지 화면만 보고 구분할 수 있다(모호한 빈 화면 0건).
- **SC-006**: 그래프 탭과 스키마 탭의 캔버스 컨트롤이 **동일 영역(캔버스 위 floating)**에 위치한다(탭 간 컨트롤 위치 불일치 0건). "테이블 보기"가 좌측 패널 바닥에 남아 있지 않다.

## Assumptions

- 접근한 정확한 줄은 분석 시점에 이미 그래프(읽기/쓰기 관계의 근거 줄)로 영속되어 있다 — 정규식 기반 링킹 경로에서 확인됨. (LLM 보강 경로가 만든 관계도 같은 근거 줄을 채우는지는 구현 단계에서 라이브 1회 확인한다.)
- 코드 노드는 시작 줄·끝 줄을 모두 보유한다(분석 산출물의 기본 필드).
- 이 기능은 기존 분석 그래프와 디스크에 남은 원본 소스를 전제로 한다(이미 spec 043에서 서버가 디스크 원본을 서빙하도록 구성됨).
- 비개발자 설계자가 1차 사용자다.

## Dependencies *(boundary)*

- **공유 계약(catalog 참조 조회)**: 테이블 참조 응답이 각 참조의 **코드 노드 끝 줄**과 **접근한 정확한 줄**(DBMS는 접근 구문의 오너 루틴 범위)을 함께 내보내야 한다. 현재 응답은 시작 줄만 내보내고 끝 줄·접근 줄을 누락한다 — 이 계약 보강이 이 기능의 전제다. (path → service 권위표는 게이트웨이 라우트 테이블.)
- **분석 백엔드**: 변경 최소 — 접근 줄은 이미 영속됨. LLM 보강 관계의 근거 줄 채움 여부만 라이브 확인.
