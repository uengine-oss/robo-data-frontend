# Phase 0 Research: 진행바 라이브화

## R1. 왜 점근식(asymptotic)인가
- **결정**: 라이브 보간 = `progress += (cap - progress) * K` (cap=다음 단계 경계−ε).
- **근거**: 한 단계의 **총 처리 건수를 사전에 알 수 없다**(FR-004). 선형 채움(`처리수/총수`)은 총수가 필요해 불가. 점근식은 매 신호가 남은 간격의 고정 비율을 메워 **총량 미지에도 경계로 수렴**(도달은 안 함) → "멈춤 없음"과 "경계 초과 없음"을 동시 충족.
- **대안 기각**: ① 선형(총수 필요·불가) ② 시간기반 타이머 애니메이션(실제 진척과 무관=정직성 위반, Constitution IV) ③ 인디터미네이트 스피너(% 바 요구와 불일치).

## R2. 단조성·경계 불변식
- **결정**: 보간은 `cap > progress`일 때만 증가. node_done 베이스라인 = `min(99, d/N*100)`은 직전 cap(=다음 경계−ε) **이상** → 역행 0. 전체 99% 상한 유지, 완료 시에만 100%.
- **근거**: 진행바 역행/리셋은 강한 불신 신호. 단조는 SC-002/003의 핵심.

## R3. 신호 가용성(실데이터)
- **결정**: processing_event는 긴 단계에 충분히 자주 옴. framework 실측: 코드 분석 단계(step6) 처리 신호 **268건**(+step5 26·step7 다수). dbms는 묶음(Batch) 단위로 옴(spec 029에서 Batch 비건너뛰기 반영됨).
- **근거**: `logs/analysis.run/latest/analyzer.log` 실측(spec 029 조사).

## R4. K/ε 기본값
- **결정**: `K=0.12`, `ε=0.5%`(경계 직전까지). 한 단계 수백 건이면 cap에 시각적으로 충분히 수렴, 적은 건수에서도 눈에 띄게 전진.
- **근거**: 268건 기준 (1-0.12)^n → 수십 건 내 cap의 95%+ 도달. 값은 plan-time 휴리스틱(clarify 불요), 필요 시 미세조정.

## R5. 028/029와의 관계
- **결정**: 진행바(`currentPhaseProgress`)는 단계 라벨(`currentPhaseIndex`, 028)·콘솔 메시지(029)와 **독립 상태**. 같은 핸들러(`applyProcessingEvent`)에 보간 한 줄 추가하되 028 블록·029 메시지 로직 불변.
- **근거**: 코드상 세 ref가 분리(currentPhaseIndex/currentPhaseProgress/메시지) → 회귀 위험 낮음.

## 검증 가용성
- framework: 실데이터/주입으로 단조성·경계 검증 가능.
- dbms: 코드분석 데이터 없음(test=스키마만) → 신호 주입/로직 검증, 라이브는 소스 확보 시(미검증 명시).
