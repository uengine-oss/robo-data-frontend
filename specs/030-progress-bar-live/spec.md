# Feature Specification: 분석 진행바(%) 라이브화 — 긴 단계 프리즈 해소

**Feature Branch**: `030-progress-bar-live`

**Created**: 2026-06-27

**Status**: Draft

**Input**: User description: 분석 진행 화면의 퍼센트 진행바가 가장 긴 코드분석 단계(수 분) 동안 멈춰 보인다. spec 028(단계 라벨)·029(콘솔 메시지)는 라이브화됐지만 진행바는 여전히 프리즈. 같은 뿌리(긴 단계 동안 단계완료 신호 공백)를 처리 단위 신호로 메워 바도 부드럽게 전진시킨다.

## 배경 / 현재 동작 (왜 필요한가)

분석 진행 화면에는 ①7단계 라벨 ②**퍼센트 진행바** ③콘솔 메시지가 있다. 진행바는 **완료된 단계 수 ÷ 전체 단계 수**로 계산되고, "완료" 신호는 한 단계가 끝날 때만 온다. 가장 긴 "코드 분석" 단계는 내부적으로 **하나의 단계**라, 그 단계가 끝날 때까지 완료 신호가 없어 **바가 수 분간 한 칸도 안 움직이다가** 끝나면 한꺼번에 점프한다. 사용자에겐 "멈춘 것"처럼 보인다.

**확인된 사실(코드)**: 진행바 = `완료 단계수 / 전체 단계수`(전략별 14/13), 완료 단계수는 **단계 완료(node_done) 때만** 증가. 코드 분석 단계 내내 처리 단위 신호(processing_event)는 **수백 건 흐르지만**(spec 029가 이미 콘솔에 활용) 진행바엔 반영 안 됨. spec 028은 단계 라벨을, 029는 메시지를 라이브화했으나 **진행바 %는 미해결**.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 긴 단계에서도 진행바가 움직인다 (Priority: P1)

분석이 가장 긴 코드 분석 단계를 지나는 동안에도, 진행바가 **조금씩 부드럽게 차오른다**. 사용자는 "멈춘 게 아니라 계속 진행 중"임을 바만 봐도 안다.

**Why this priority**: 진행바는 진행 화면에서 가장 눈에 띄는 안심 신호다. 가장 긴 구간의 프리즈가 "멈춤" 오해의 핵심.

**Independent Test**: 코드 분석 단계 구간에서 처리 단위 신호를 흘리며 진행바 값이 단조 증가하는지(멈추지 않는지) 확인.

**Acceptance Scenarios**:

1. **Given** 분석이 코드 분석 단계 진행 중(단계 완료 신호 없음), **When** 처리 단위 신호가 계속 도착, **Then** 진행바 값이 **증가**한다(이전과 달리 정지 아님).
2. **Given** 코드 분석 단계 진행 중, **When** 처리 단위가 매우 많이 도착, **Then** 진행바는 **다음 단계 경계를 넘지 않는다**(완료 전 100% 도달 금지, 현행 99% 상한 유지).
3. **Given** 코드 분석 단계가 실제로 완료(단계 완료 신호 도착), **When** 다음 단계로 넘어감, **Then** 진행바가 그 단계 몫만큼 채워지고 **역행하지 않는다**.

---

### User Story 2 - 전 단계·전 전략에서 자연스러운 진행 (Priority: P2)

진행바 라이브화가 특정 단계·전략에 한정되지 않고, 처리 단위 신호가 오는 어느 단계에서든(특히 긴 단계) 동일하게 동작한다(framework·dbms 공통).

**Why this priority**: 일관성. 코드 분석 외 다른 긴 단계(예: 후처리)에도 같은 원리가 적용돼야 한다.

**Independent Test**: 서로 다른 단계의 처리 신호 주입 시 모두 현재 단계 슬롯 안에서 바가 차오르는지 확인.

**Acceptance Scenarios**:

1. **Given** 임의의 단계에서 처리 단위 신호가 옴, **When** 신호가 누적, **Then** 진행바가 그 단계 슬롯(전체의 1/단계수) 범위 안에서 차오른다.
2. **Given** dbms 전략, **When** 묶음(배치) 처리 신호가 옴, **Then** framework와 동일하게 진행바가 라이브 전진한다(전략 분기 없음).

---

### Edge Cases

- 한 단계의 **총 처리 건수를 미리 모른다** → 점근적(asymptotic)으로 슬롯을 채우되 경계를 절대 넘지 않음(언제 끝날지 몰라도 자연스럽게 수렴).
- 처리 신호가 한 건도 없는 짧은 단계 → 기존 단계완료(node_done) 전진으로 정상 동작(라이브 보간은 없어도 무방).
- 단계 완료 신호가 라이브 보간보다 **늦게/빨리** 와도 진행바는 **단조**(역행 0). 완료 시 그 단계 몫까지 채움.
- 분석 전체 완료 → 100% 보정(현행 유지).
- 분석 재시작 → 0%로 리셋(현행 유지).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 진행바는 긴 단계(처리 단위 신호가 지속되는 단계) 동안 **증가**해야 한다(정지 금지).
- **FR-002**: 라이브 전진의 원천은 **처리 단위 신호(processing_event)** 여야 한다(spec 029가 쓰는 동일 신호). 별도 백엔드 신호/엔드포인트 추가 없음.
- **FR-003**: 진행바는 **현재 단계 슬롯**(전체의 1/단계수) 안에서만 라이브로 차오르고, **다음 단계 경계를 넘지 않아야** 한다(완료 전 100% 금지, 99% 상한 유지).
- **FR-004**: 한 단계의 총 처리 건수를 모르는 상태에서도 자연스럽게 차오르도록 **점근적 채움**(또는 동등 효과) 이어야 한다 — 건수가 늘수록 경계에 수렴하되 도달은 단계 완료 시.
- **FR-005**: 단계 완료(node_done) 기반 전진은 **유지**되며, 라이브 보간과 충돌해 **역행하지 않아야** 한다(진행바 단조 증가 불변).
- **FR-006**: framework·dbms **공통**으로 동작해야 한다(전략 분기 없음).
- **FR-007**: spec 028(단계 라벨 전진)·029(콘솔 메시지)의 동작을 **훼손하지 않아야** 한다(같은 핸들러 영역, 별개 관심사).
- **FR-008**: 분석 시작/재시작 시 진행바 리셋, 전체 완료 시 100% 보정(현행 보존).

### Key Entities

- **진행바 값(currentPhaseProgress)**: 0~100 사이 단조 증가 백분율. 표시 전용 런타임 상태.
- **완료 단계 수 / 전체 단계 수**: 진행바의 단계-기반 베이스라인(현행).
- **처리 단위 신호(processing_event)**: 현재 단계 내 진척의 라이브 원천(건수).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 가장 긴 단계 구간에서 진행바가 **0회 정지**(처리 신호 도착마다 값이 증가하거나 최소한 정지하지 않음) — 현재는 그 구간 내내 동일 값.
- **SC-002**: 진행바는 분석 동안 **한 번도 감소·리셋되지 않는다**(시작/재시작 제외).
- **SC-003**: 진행바는 분석 완료 전 **100%에 도달하지 않는다**(단계 경계·99% 상한 준수).
- **SC-004**: framework·dbms 양쪽에서 동일 동작(전략별 분기 0).
- **SC-005**: spec 028·029 동작 **회귀 0**(단계 라벨·콘솔 메시지 변화 없음).

## Assumptions

- 처리 단위 신호(processing_event)는 긴 단계 동안 충분히 자주 도착한다(framework 실측: 코드 분석 단계 수백 건). dbms도 묶음 단위로 도착.
- 한 단계의 총 처리 건수는 사전에 알 수 없다 → 점근적 채움으로 처리.
- dbms는 현재 코드분석 실데이터가 없어(스키마만) 라이브 실증 불가 → 신호 주입/로직으로 검증, 라이브는 dbms 소스 확보 시(미검증 명시).
- 이 스펙은 spec 028(완료)·029(완료)의 같은 뿌리 후속이며, C(테이블 끝점)·http(스트림 오류 절단)는 별도 스펙.
