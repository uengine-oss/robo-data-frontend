# Feature Specification: 진행 단계 = "지금 진행 중" 정확 표시 + 퍼센트 정수화

**Feature Branch**: `032-phase-active-running`

**Created**: 2026-06-27

**Status**: Draft

**Input**: 앱 실측 발견 — ① 단계 표시가 **완료된 단계에 머물러** 있음(예: AST 적재 끝나고 코드베이스 스캔 중인데 활성 표시가 AST 적재에 멈춤), 일부 단계는 한 번에 점프. ② 진행바 퍼센트가 **소수점 과다**(`58.53085714285714%`). 028/030 의 같은뿌리 후속 정정.

## 배경 / 현재 동작 (왜)

진행 패널은 `currentPhaseIndex`를 "활성(진행 중) 단계"로 표시한다(그 앞=완료 ✓, 같음=진행중 ▶, 뒤=대기). 그런데:
- **단계 지연**: `currentPhaseIndex`를 **방금 완료된 leaf 의 단계**로 세팅했다(spec 026). 그래서 AST 적재(단계1)가 끝나면 활성 표시가 단계1에 남고, 실제 진행 중인 코드베이스 스캔(단계2)이 진행중으로 안 뜬다. 완료 신호가 몰려 오면 여러 단계가 한꺼번에 점프. (spec 028은 긴 코드분석 단계만 processing 신호로 보정했을 뿐, 초반 단계 지연은 그대로.)
- **퍼센트 소수점**: spec 030 진행바 라이브 보간이 실수(float)를 만들어 화면에 `58.53085714285714%`처럼 길게 표시됨(정수 반올림 누락).

**확인된 사실(코드)**: 분석 파이프라인은 leaf step 들을 **고정 순서**로 순차 실행한다. 어떤 leaf 가 완료되면 그 **다음 leaf** 가 곧 지금 진행 중인 작업이다. 즉 "진행 중 단계 = 가장 최근 완료 leaf 의 다음 leaf 의 단계"로 도출하면 완료 단계에 머물지 않고 정확히 다음을 진행중으로 표시할 수 있다(다중 leaf 단계는 그 단계의 마지막 leaf 가 끝나야 다음으로 넘어감 → overshoot 없음). 긴 코드분석 단계도 "다음 미완료 leaf = 코드분석"이라 그 단계가 자동으로 진행중 표시(spec 028 의 processing 신호 보정 불필요).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 끝난 단계 말고 지금 단계가 진행중으로 (Priority: P1)

한 단계가 끝나면 **다음 단계가 즉시 "진행 중 ▶"** 으로 표시된다. AST 적재가 끝나면 코드베이스 스캔이 진행중으로 뜨고, 완료된 AST 는 ✓ 로 내려간다.

**Why this priority**: 사용자가 직접 지목한 핵심 오표시.

**Independent Test**: leaf 완료 신호를 파이프라인 순서대로 주입 → 매 시점 활성 단계가 "방금 끝난 단계의 다음"인지 확인.

**Acceptance Scenarios**:

1. **Given** AST 적재(단계1) 완료 신호 도착, **When** 코드베이스 스캔(단계2) 실행 중(아직 완료 신호 없음), **Then** 활성 표시가 **코드베이스 스캔(단계2)**, AST 적재는 ✓ 완료.
2. **Given** 관계연결(단계3)에 leaf 가 여러 개라 그 중 하나만 완료, **When** 같은 단계의 다른 leaf 실행 중, **Then** 활성은 **여전히 관계연결(단계3)** (다음 단계로 넘기지 않음).
3. **Given** 분석 컨텍스트 구성의 마지막 leaf 완료, **When** 긴 코드 분석 실행 중, **Then** 활성은 **코드 분석(단계5)** 으로 그 단계 내내 유지.
4. **Given** 마지막 leaf(embed)까지 완료, **When** 분석 종료, **Then** 모든 단계 ✓.

### User Story 2 - 퍼센트는 정수로 (Priority: P1)

진행바 퍼센트가 **정수**로 표시된다(`59%`), 소수점 꼬리가 없다.

**Why this priority**: 직접 지목된 표시 결함.

**Independent Test**: 보간으로 float 가 된 진행값이 화면엔 정수로 보이는지 확인.

**Acceptance Scenarios**:
1. **Given** 진행바 내부값이 `58.53085714285714`, **When** 표시, **Then** `59%`(반올림 정수).

### Edge Cases
- 백엔드가 어떤 leaf 를 스킵/미전송 → "최고 완료 인덱스의 다음" 기준이라 멈추지 않고 다음 단계로 진행(견고).
- dbms 는 코드베이스 스캔 leaf 가 없음 → 그 단계는 자연히 건너뛰어 완료(✓)로 표시(전략별 leaf 순서 반영).
- 진행값 float 정밀도는 **내부 보존**(보간 지속), 표시만 반올림(보간 정지 안 함).

## Requirements *(mandatory)*

- **FR-001**: 활성(진행 중) 단계 = **가장 최근 완료 leaf 의 다음 leaf 의 단계**. 완료된 단계가 활성으로 남지 않아야 한다.
- **FR-002**: 다중 leaf 단계는 그 단계의 **마지막 leaf 완료 전까지** 활성 유지(다음 단계로 overshoot 금지).
- **FR-003**: 단계 인덱스는 **단조 증가**(역행 0). 전 leaf 완료 시 모든 단계 완료(✓).
- **FR-004**: leaf 순서는 **전략별**(framework/dbms) 고정 순서로 정의(파이프라인 단일 진실). 미상/스킵 leaf 에 견고(최고 완료 인덱스 기준).
- **FR-005**: 긴 코드 분석 단계는 별도 신호 없이도 그 단계가 진행중으로 표시(다음 미완료 leaf=코드분석). spec 028 의 processing-event 단계 승급은 **이 모델로 대체**(중복·overshoot 위험 제거).
- **FR-006**: 진행바 퍼센트는 **정수**로 표시(반올림). 내부 진행값의 float 정밀도는 보존(spec 030 보간 지속).
- **FR-007**: 단계 세부문구(현재 단계 설명)는 **진행 중(다음) leaf** 기준으로 표시(없으면 방금 완료 leaf).
- **FR-008**: spec 029(메시지)·030(진행바 라이브 보간) 동작 보존.

## Success Criteria *(mandatory)*

- **SC-001**: 한 단계 완료 시 **다음 단계가 진행중**으로 바뀜(완료 단계 활성 잔류 0).
- **SC-002**: 다중 leaf 단계에서 overshoot 0(마지막 leaf 전엔 다음 단계 활성 안 됨).
- **SC-003**: 단계 인덱스 역행 0(전 과정 단조).
- **SC-004**: 퍼센트 표시에 소수점 0(정수).
- **SC-005**: framework·dbms 양쪽 정확(전략별 leaf 순서).

## Assumptions

- 분석 파이프라인 leaf 실행 순서는 고정(analysis_pipelines.py 순서) → 프론트에 전략별 순서 배열로 인코딩. leaf 이름 = node_done emit 이름(전수조사로 STEP_TO_PHASE 키와 일치 확인).
- dbms 라이브 실증은 코드분석 데이터 없어 불가 → leaf 순서/로직 시뮬로 검증, 라이브는 소스 확보 시.
- spec 028(단계 라이브 전진)의 의도(긴 단계 표시)는 이 leaf 순서 모델이 더 정확히 달성 → 028 의 processing-event phase 승급 코드는 제거(supersede). 028 의 단계 라벨 자체(7단계)는 유지.
